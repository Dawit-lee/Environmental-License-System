# 포트폴리오 정리

기능마다 **문제 원인 / 해결 방법 / 성과**로 정리했습니다. 성과에는 PR이나 문서에 남은 **실측값만** 쓰고, 출처와 한계를 같이 적습니다. 아직 재지 않은 것은 "측정 예정"과 측정 방법만 적었습니다.

- 출처 표기: `#번호`는 이 저장소 `dev`에 병합된 PR입니다.
- 실제 사업 데이터와 회사 문서는 저장소에 없습니다. 실제 사례로 잰 숫자는 집계값만 옮겼습니다.
- 개발은 AI 코딩 도구(Claude Code)와 함께 했습니다. 요구사항·설계 판단·법령 기준 확인·검수 기준은 직접 정했습니다.
- **범위 재조정:** 설계사 실무자로서 운영단계 배출 측정·이행은 설계사가 아니라 운영사 업무라고 판단해, 운영 기능을 프로젝트별 선택 모듈(기본 꺼짐)로 돌리고(#49) 프로젝트 중심 인허가 + 설계 일정 관리에 집중했습니다. 운영 기능은 성과로 쓰지 않습니다.
- **설계 일정 기능의 실무 근거:** 실무에서 분야별 주간공정보고를 취합하고 전체 공정을 관리한 경험에서 나온 기능입니다.

## 1. 인허가 자동 도출

**문제 원인**
- 환경기초시설 한 건에 인허가가 수십 건 걸립니다. 어떤 인허가가 필요한지는 시설용량·부지면적·공사비·용도지역·추진주체 같은 속성을 법령 기준값과 하나씩 대조해야 알 수 있고, 현업은 이를 엔지니어가 법령을 읽어 엑셀 검토서로 만듭니다.
- 검토서는 작성 시점에 고정되어, 법령이 바뀌어도 어느 판정이 영향을 받는지 추적되지 않습니다.
- LLM에 판정을 맡기면 실행마다 결과가 달라지고 근거를 추적하기 어려워 반복 측정이 안 됩니다.

**해결 방법**
- 판정은 규칙 엔진이 결정적으로 계산합니다(조건 JSON, 참/거짓/모름 3값). 값이 없으면 "판정 보류"와 필요한 입력을 보여 주고 추정하지 않습니다.
- 규칙마다 기준값과 근거 조문을 법령 본문(국가법령정보센터 현행 본문·별표)에서 확인해 `source_ref`·`source_quote`로 저장하고, 판정 사유를 조건에서 자동 생성합니다.
- 판정 결과는 공통 검토 통로를 거쳐 승인된 것만 인허가 대장에 들어가고, 근거 법령이 자동으로 개정 감시 대상이 됩니다.
- 실제 사업의 인허가 목록과 대조하는 골든 하네스를 만들고, 실제 데이터는 `GOLDEN_DIR`로 레포 밖에 둡니다.

**성과**

| 지표 | 규칙 v1 (14개) | v2 (34개) | v3 (48개) | v4 (51개) | 출처 |
|---|---|---|---|---|---|
| 재현율(엄격) | 1.3% (1/77) | 28.6% (22/77) | 48.1% (37/77) | **50.6% (39/77)** | #46, #47, #61 |
| 재현율(포괄 인정: 통합환경허가 의제 포함) | — | 36.4% (28/77) | 55.8% (43/77) | 58.4% (45/77) | #46, #47, #61 |
| 재현율(완화: 판정 보류 포함) | 2.6% (2/77) | 44.2% (34/77) | 66.2% (51/77) | 68.8% (53/77) | #46, #47, #61 |
| 오탐(해당 아님을 해당으로) | 0 | 0 | 0 | 0 | #46, #47, #61 |
| 정밀도(정답과 대조된 출력 중) | 1/1 | 20/20 | 30/30 | 32/32 | #46, #47, #61 |
| 규칙 표 테스트(경계값·보류) | — | 78행 | 128행 | — | #46, #47 |

> **한계:** 사례는 소각시설 증설 **1건**이고, 규칙은 그 사례에서 빠진 인허가 종류를 **본 뒤에** 썼습니다. 그래서 이 숫자는 **알고 있는 사례에 대한 커버리지**이지, 처음 보는 사업에 대한 정확도(블라인드 테스트)가 아닙니다. 기준값은 사례가 아니라 법령 본문에서 가져왔고, 사례의 속성값은 바꾸지 않았습니다. 정밀도의 분모는 정답 목록과 대조된 출력만이며, 두 번째 사례가 없어 일반화된 정밀도는 아직 없습니다.

| 측정 예정 | 측정 방법 |
|---|---|
| 처음 보는 사업에 대한 재현율·오탐 | 규칙을 고정한 상태에서 두 번째 실제 사례를 골든 하네스로 1회 측정(규칙 수정 전 값 기록) |
| 프로젝트 1건 인허가 검토 시간 | 같은 사업으로 엑셀 검토서 작성 시간 vs 속성 입력 → 도출 → 검토 완료 시간(승인 이벤트 시각) |
| 실무자 평가 | 설계 실무자 2~3명에게 도출 결과를 보여 주고 빠진 것·불필요한 것·근거 표시의 유용성을 질문지로 수집 |

## 2. 협의의견·허가조건 AI 추출 + 사람 검토

**문제 원인**
- 환경영향평가 협의의견서와 허가증의 조건은 수십 개이고, 담당자가 읽어서 설계 반영·이행 기한을 따로 챙겨야 합니다. 옮겨 적는 과정에서 누락이 생깁니다.
- LLM은 문서에 없는 의무를 지어내거나 문구를 바꿔 적을 수 있어 그대로 대장에 넣을 수 없습니다.

**해결 방법**
- 조건마다 원문 조건번호와 인용문을 같이 뽑게 하고, 인용문을 PDF 글자층과 대조해 다르면 "환각 의심"으로 맨 위에 올립니다. 글자층이 없는 스캔본은 원문 페이지를 열어야 승인 버튼이 켜집니다.
- 승인 / 수정 후 승인 / 승인 요청 / 거절, 일괄 승인, 추가 전용 감사 로그. AI 원본과 검토자 수정본을 따로 저장합니다.
- 제공자를 Claude / Gemini / OpenAI 중 서버 설정으로 고르게 하고, 같은 정답표로 비교하는 평가 스크립트를 만들었습니다.

**성과** (출처: #45, [EXTRACTION_EVAL_RESULTS.md](EXTRACTION_EVAL_RESULTS.md))

| 제공자 | 재현율: 텍스트 PDF 2건 (106조건) | 재현율: 이미지 변환본 1건 (44조건) | 정밀도 |
|---|---|---|---|
| Claude (`claude-sonnet-5-5`) | 91.5% (97/106) | 75.0% (33/44) | 100% |
| Gemini (`gemini-3.6-flash`) | 39.6% (42/106) | 25.0% (11/44) | 100% |
| OpenAI (`gpt-6.1-terra`) | 100% (106/106) | 100% (44/44) | 100% |

- 측정 전체 비용: 기록된 토큰 수 × 단가로 계산해 약 **$2.44**(Claude $1.76 — 잘린 실패 호출 2회 $0.53 포함, OpenAI $0.55, Gemini $0.14).

> **한계:**
> - 정답표는 Claude가 PDF 글자층에서 만든 초안을, 고치기 전에 글로 정한 분할·주기 규칙으로 **2차 검토**한 것입니다(2026-11-15). 106행 모두 원문과 항목 수·순서·내용이 일치했고 **주기 3칸만** 바뀌었으며, 저장된 응답을 다시 채점해 재현율·정밀도는 그대로였습니다. 다만 **2차 검토도 Claude가 했고 분야 전문가(사람)의 검수는 없습니다.** Claude가 만든 정답으로 Claude를 채점하는 편향이 남아 있습니다.
> - 문서당 **1회** 실행입니다. 반복 측정이 아니어서 실행마다 값이 달라질 수 있습니다.
> - "스캔본"은 실제 스캔이 아니라 텍스트 PDF를 150dpi 이미지로 바꾼 사본이라 실제 스캔보다 깨끗합니다.
> - 정밀도 100%는 "정답표 범위 안에서 문서에 없는 의무를 지어내지 않았다"는 뜻입니다.
> - 조건번호 일치율은 이 문서들에서 의미가 없습니다(조건마다 번호가 없고 목차 아래 항목이 나열됨, 3사 모두 정확 일치 0%).
> - Gemini·OpenAI 단가는 공식 가격표로 확인하지 않았습니다. 문서는 공개된 환경영향평가 협의내용이며 회사 문서는 쓰지 않았습니다.

**실측이 찾은 결함:** Claude 어댑터의 첫 실제 PDF 추출이 2회 모두 실패했습니다. 출력 상한 16,000토큰 중 사고에 8,138토큰이 나가 23쪽 문서의 5쪽에서 답이 잘렸습니다. 상한을 64,000으로 올리고 스트리밍 호출로 바꾼 뒤 3건 모두 1회에 성공했습니다(출력 26,083 ~ 35,716토큰). 이 수정은 실제 호출 3건으로 확인했고, 이 클래스의 자동 테스트는 없습니다(#45).

| 측정 예정 | 측정 방법 |
|---|---|
| 전문가가 검수한 정답표 기준 재현율·정밀도 | 정답표의 경계 행을 분야 전문가가 검수한 뒤 같은 3건을 제공자별 3회씩 재실행해 평균·범위 |
| 조건번호가 있는 허가증에서의 번호 일치율 | 조건마다 번호가 있는 공개 허가증으로 별도 측정 |
| 문서 1건 검토 시간 | 같은 문서로 수기 정리 시간 vs 추출 결과 검토·승인 시간 |
| 승인 시 수정 비율 | 운영 데이터에서 `EDITED_ACCEPTED / (ACCEPTED + EDITED_ACCEPTED)` |

## 3. 허가증·협의의견 버전 비교

**문제 원인**
- 변경허가·재협의로 새 판이 나오면 수십 개 조건을 이전 판과 한 줄씩 대조해야 하고, 숫자 하나 바뀐 조건("50 → 30ppm")은 문구가 거의 같아 놓치기 쉽습니다.
- 새 판을 통째로 다시 등록하면 기존 의무의 이행 기록이 끊기고 알림이 중복됩니다.

**해결 방법**
- 조건번호로 먼저 짝을 맞추고 문장 유사도로 확인하는 결정적 엔진(AI 없음). 숫자·단위·이상/이하·주기가 다르면 유사도와 상관없이 "변경", 말투만 다르면 "경미"로 묶어 한 번에 승인.
- 변경은 같은 의무를 고쳐 써서 이력 유지, 삭제는 "원문에 없음 확인" 체크 필수·일괄 승인 불가. 대장 반영과 현장 반영을 따로 추적.

**성과**

| 측정 예정 | 측정 방법 |
|---|---|
| 판정 정확도 | 실제로 개정된 공개 허가증·협의의견 쌍으로 사람이 만든 정답(추가/삭제/변경/경미)과 비교 |
| 버전 대조 시간 | 같은 문서 쌍으로 수기 대조 vs 비교 화면 검토 |

지금 있는 근거는 경계값 단위 테스트(`DiffEngineTest`)와 승인 API 테스트뿐입니다(#17, #19, #21).

## 4. 법령 개정 알림

**문제 원인**
- 법령 개정을 사람이 찾아봐야 하고, 알아도 어느 프로젝트의 어느 인허가에 영향이 있는지 바로 알 수 없습니다.
- 실무 기준은 시행규칙에 많은데 법률만 보면 놓치고, 공포일과 시행일이 달라 시행 시점 대응이 빠집니다.

**해결 방법**
- 법제처 Open API에서 법령마다가 아니라 **날짜별 변경 목록**을 하루 한 번 받아 감시 법령만 남깁니다. 감시 법령이 늘어도 호출 수가 거의 같습니다.
- 실제 응답에 과거 버전(연혁) 행이 섞여 나오는 것을 확인하고, "현행이면서 저장된 MST보다 새 버전"만 개정으로 판정했습니다.
- 마지막 성공일 커서로 장애 뒤 밀린 날짜를 자동 처리(최대 31일), 2회 연속 실패 시 관리자 알림.
- 지정 조문이 바뀌면 직접 영향, 같은 법의 다른 조문만 바뀌면 참고. 시행일을 기한으로 등록. 직접 입력·AI 추출·자동 도출 세 경로의 법령 연결이 모두 감시 대상이 됩니다.

**성과**

| 측정 예정 | 측정 방법 |
|---|---|
| 개정 감지 소요 | 운영 기간 중 `detected_on − 공포일` 분포 |
| 영향 인허가 식별 누락 | 실제 개정 N건을 골라 사람이 찾은 영향 인허가와 시스템 결과 비교 |
| 알림 노이즈 | 직접 영향 중 담당자가 "영향 없음"으로 확인한 비율 |
| 배치 안정성 | 월간 미처리 날짜 수 |

테스트는 녹화한 법제처 응답 픽스처로 돌립니다(#10, #14).

## 5. 프로젝트 중심 구조와 권한

**문제 원인**
- 인허가는 시설이 아니라 프로젝트 단위로 생기는데, 진행 현황·기한·담당자·문서·검토 대기가 화면마다 흩어져 있었습니다.
- 회사마다 결재 방식이 달라 직급명으로 승인 권한을 정하기 어렵습니다.

**해결 방법**
- 프로젝트 화면의 탭(개요·인허가·의무사항·AI 검토·법령 영향·일정·문서·설정)과 사람별 "내 할 일"로 정리(#26, #29, #31).
- 같은 회사는 목록·개요 열람, 멤버만 쓰기. 승인 권한은 멤버별 플래그(혼자 승인 / 일괄 승인 / 프로젝트 관리).
- 운영단계 기능은 운영사 업무로 보고 프로젝트별 선택 모듈로 분리, 기본 꺼짐(#49).

**성과**

| 지표 | 값 | 출처 |
|---|---|---|
| 통합 QA | 병합된 약 20개 PR을 합친 `dev`를 브라우저로 전 구간 점검, **12건 수정**(보안 1건 포함, 일부는 문구·빠진 기능) | #48 |
| 타 회사 접근 점검 | 다른 회사 사용자·같은 회사 비멤버로 모든 GET·쓰기 API 호출, **데이터 노출 없음**. 찾은 1건(제안 버전 409로 id 존재 노출)은 403으로 수정 | #48 |

> **한계:** 점검은 사람이 정한 시나리오로 한 번 했고 자동 보안 스캔은 아닙니다. 존재하지 않는 id는 404, 남의 id는 403이라 id 존재 여부는 아직 구분됩니다(#48에 남긴 항목).

## 6. 분야별 설계 일정

**문제 원인**
- 설계 일정이 엑셀 예정공정표와 주간 보고 문장에 나뉘어 있어 "무엇이 기준보다 며칠 늦었고 왜"가 구조화되어 남지 않습니다.
- 일정이 입찰일·계약일·현장설명일 같은 기준일에서 "+150일", "−15일"로 정해지는데, 기준일이 바뀌면 엑셀에서 관련 날짜를 하나씩 고쳐야 합니다.
- 분야 간 인계가 늦으면 후행 분야가 다음 회의에서야 알고, 협력사·발주처 보고회·출장 일정은 사람마다 다른 달력에 흩어집니다.
- 실무 근거: 분야별 주간공정보고를 취합하고 전체 공정을 관리하면서 겪은 문제입니다.

**해결 방법** (#49, #50, #53–#59)
- **분야별 일정 + 간트:** 회사 공통 분야 목록, 일정 항목·마일스톤·FS 선후행(순환 금지), 간트(MIT 라이브러리 SVAR React Gantt를 감싼 것). 선행 항목이 기한을 넘기면 후행 담당자에게 알림 1회(#50).
- **기준일·오프셋, 기준 확정, 지연 계산:** 항목을 "기준일 ± 일/개월"로 두고, 기준일을 바꾸면 미리보기로 이동 건수·전후 날짜를 확인한 뒤 미완료 항목만 옮깁니다. 기준 계획을 확정(재확정은 사유 필수)하고, 상태·지연 일수는 저장하지 않고 조회 때 계산합니다. 지연 현황 표는 주간 보고용으로 복사됩니다. 기준일은 착수·계약·입찰·심의·완료 + 현장설명일·적격자 통보일·착공일(#54, #59).
- **이벤트·출장:** 보고회·심의·출장 등 이벤트와 참석자, 프로젝트 달력과 회사 달력(부서·팀·종류 필터, 사람별 이번 주 출장·심의)(#53).
- **협력사 읽기 전용 공유:** 로그인 없는 링크(256비트 토큰, DB엔 해시만, 만료·회수·분야 범위), `.ics` 구독, 인쇄본. 응답 필드는 화이트리스트(#57).
- **Google 캘린더 단방향 동기화:** 사용자가 켤 때만, 앱이 만든 보조 캘린더로 앱 → Google 한 방향. DB 트리거 outbox + 재시도(#56).
- **문서 → 일정 제안:** 공고문·현장설명서·과업내용서·공문·회의록에서 날짜를 근거 문장·쪽과 함께 뽑아, 기존 "AI 제안 → 사람 승인" 통로로 보냅니다. 승인한 행만 일정 항목·이벤트가 되고, 비슷한 기존 항목은 갱신이 기본이라 두 번 추출해도 중복이 생기지 않습니다(#58, #59).
- **인허가 진행 현황 1쪽(XLSX):** 인허가 대장에서 A4 1쪽 보고 표를 바로 내려받습니다(#55).

## 이력서용 문장

데이터가 받쳐 주는 것만 썼습니다.

1. 환경기초시설 인허가 관리 웹앱을 Spring Boot 3 · React 18 · PostgreSQL로 설계·구현하고(AI 코딩 도구 활용), 실제 DB(Testcontainers) 위 API 테스트 중심으로 백엔드 테스트 887개를 유지했다.
2. 인허가 자동 도출을 LLM 대신 결정적 규칙 엔진(참/거짓/모름, 판정 보류)으로 만들고, 법령 본문에서 기준값을 확인한 규칙을 14 → 51개로 늘려 실제 소각시설 증설 사례 1건의 인허가 목록 대비 커버리지를 1.3% → 50.6%(39/77, 오탐 0)로 넓혔다.
3. 협의의견서 조건 추출을 Claude·Gemini·OpenAI 교체형 어댑터로 구현하고 공개 문서로 3사를 비교 측정했으며(텍스트 PDF 재현율 91.5% / 39.6% / 100%, 스캔 변환본 75.0% / 25.0% / 100%, 정밀도 모두 100%. 문서당 1회 실행이며, 정답표는 규칙 기반 2차 검토에서 106행 모두 원문과 일치했지만 검토도 Claude가 해 전문가 검수는 없음), 첫 실측에서 Claude 응답이 사고 토큰 때문에 잘리는 결함을 찾아 고쳤다.
4. AI 추출·자동 도출·버전 비교 결과를 하나의 "제안 → 사람 승인" 통로와 추가 전용 감사 로그로 묶어, 승인 없이 대장에 반영되는 경로를 구조적으로 없앴다.
5. 법제처 Open API를 날짜별 변경 목록으로 하루 한 번 조회하고, 실제 응답에 섞인 과거 버전 행을 걸러 내는 개정 감지 배치(커서 기반 자동 복구)를 만들었다.
6. 실제 사업 데이터는 레포 밖(`GOLDEN_DIR`)에 두고 공개 저장소에는 가상 데이터만 두는 측정 하네스로, 대외비를 공개하지 않고 실제 사례로 정확도를 쟀다.
7. 설계사 실무자로서 운영단계 배출 측정은 운영사 업무라고 판단해 운영 기능을 기본 꺼진 선택 모듈로 돌리고, 프로젝트 중심 인허가 + 분야별 설계 일정 관리로 범위를 다시 잡았다.
8. 주간공정보고 취합·전체 공정 관리 실무를 바탕으로 분야별 설계 일정(기준일·오프셋 간트, 기준 확정·지연 계산, 이벤트·출장 달력, 협력사 읽기 전용 링크·ICS, 선택형 Google 캘린더 단방향 동기화, 인허가 진행 현황 1쪽 XLSX)을 만들고, 문서 → 일정 추출을 기존 "AI 제안 → 사람 승인" 통로에 붙였다(실제 현장설명서 1건, 규칙 기반 5/5).

## 쓰지 않을 것

- **"인허가 판정 정확도 51%"처럼 일반 정확도로 읽히는 표현.** 사례 1건, 규칙을 놓친 것을 본 뒤에 쓴 커버리지입니다.
- **"OpenAI가 가장 정확" 같은 제공자 순위 일반화.** 정답표는 Claude가 만들고 Claude가 2차 검토했을 뿐 전문가 검수가 없고, 문서 2건(+변환본 1건), 1회 실행입니다.
- **"환각 0%".** 정밀도 100%는 전문가 검수 전 정답표 범위 안의 값입니다.
- **시간 절감·업무 효율 수치, 실무자 반응.** 아직 재지 않았습니다.
- **운영단계 기능(측정값·초과 판정·시정 업무·이행 보고서).** 운영사 업무이고 기본 꺼진 선택 모듈입니다.
- **설계 일정 기능의 시간 절감·정확도.** 아직 재지 않았습니다. 문서 → 일정 추출의 가상 세트 수치(같은 세트로 보정한 개발용)도 성과로 쓰지 않습니다.
- **Google 캘린더 연동을 실제로 운영했다는 표현.** 실제 Google 호출은 아직 없습니다.
- **간트 드래그·주/월 보기를 직접 만든 것처럼 쓰는 것.** SVAR 라이브러리 기능입니다.
- **혼자 손으로 모든 코드를 썼다는 표현.** AI 코딩 도구를 썼습니다.
- **배포·운영 경험, CI.** 아직 없습니다.
- **실제 사업명·발주처·협력사 이름, 회사 문서 내용.**
