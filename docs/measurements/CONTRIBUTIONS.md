# 기능별 측정 결과 (2026-11-11)

"구현하고 테스트로 검증했다"로만 적혀 있던 기능 6개를 합성 데이터로 재 본 결과입니다. 숫자는 모두 아래 명령을 실제로 돌려 나온 값이고, 측정에서 드러난 문제는 고치지 않고 [드러난 문제](#드러난-문제-고치지-않음)에 적었습니다.

## 실행 방법

```bash
cd backend
./gradlew measure                                # 전체 (약 3분)
./gradlew measure --tests '*DiffMeasurement'     # 하나만
```

결과는 `backend/build/measurements/results.txt`와 표준 출력(`[MEASURE]`)에 남습니다. 측정 테스트는 `@Tag("measurement")`라서 `./gradlew test`와 CI에서는 돌지 않습니다.

## 공통 조건

- 장비: Apple M4(10코어), 메모리 16GB, macOS. Docker 29.5.2(VM 10 CPU, 7.75GB).
- DB: Testcontainers `postgres:16-alpine`, 앱과 같은 Flyway 스키마. 커넥션 풀은 HikariCP 기본값 10.
- 앱: Spring Boot 3.5.16, Java 17, 테스트 JVM 힙 최대 512MB. 메일·법제처·LLM은 테스트용 대역(가짜 구현)입니다.
- 데이터: 전부 합성입니다. 회사 자료와 `raw/`는 쓰지 않았습니다. 난수 seed는 20261111로 고정했습니다.
- 정답 라벨: 표본을 **어떻게 만들었는지**가 정답입니다(원문에서 복사했다, 숫자를 바꿨다 등). 측정 대상 로직의 출력으로 정답을 만들지 않았습니다.
- 시간: 같은 JVM에서 3~5회 반복한 중앙값입니다. 첫 회는 JVM이 덜 데워져 느리므로 최소~최대를 함께 적었습니다. 실행할 때마다 수십 % 달라집니다.

합성 허가 조건은 `SyntheticPermit`이 만듭니다. 시설 12종 × 물질 10종의 조합마다 조건 하나를, 문장 틀 3종(농도 한도 / 측정·보고 주기 / 기록 보존) 중 하나로 씁니다. 한 문서 안에서 같은 조합은 한 번만 나옵니다.

## 1. 인용문 원문 대조 (`QuoteChecker`)

AI가 낸 인용문이 원문 해당 쪽(±1쪽)에 있는지 대조해 "원문에 있음 / 환각 의심 / 확인 불가"로 나누는 로직입니다. LLM을 부르지 않고 대조 로직만 쟀습니다.

**방법** (`QuoteCheckMeasurement`): 합성 허가증 10건(6쪽씩, 쪽당 조건 10개, 쪽 경계에 걸친 문장 1개씩)을 만들고 인용문 290건을 섞었습니다.

| 분류 | 만든 방법 | 표본 | 원문에 있음 | 환각 의심 | 확인 불가 |
|---|---|---|---|---|---|
| 정상 | 원문에서 그대로 복사 | 20 | 20 | 0 | 0 |
| 정상 | 띄어쓰기만 다름(공백 삭제·중복·줄바꿈) | 20 | 20 | 0 | 0 |
| 정상 | 쪽 번호가 1쪽 어긋남 | 20 | 20 | 0 | 0 |
| 정상 | 쪽 경계에 걸친 문장 | 20 | 20 | 0 | 0 |
| 지어냄 | 그 문서에 없는 시설·물질 조합으로 만든 조건 | 60 | 0 | 60 | 0 |
| 뜻 변경 | 복사 후 숫자 변경 | 20 | 0 | 20 | 0 |
| 뜻 변경 | 복사 후 주기 변경(분기→반기 등) | 20 | 0 | 20 | 0 |
| 뜻 변경 | 복사 후 "이하"→"미만" | 20 | 0 | 20 | 0 |
| 표기만 다름 | 어미 변경(하여야 한다→할 것) | 12 | 0 | 12 | 0 |
| 표기만 다름 | 전각 숫자 | 12 | 0 | 12 | 0 |
| 표기만 다름 | 마침표 생략 | 12 | 12 | 0 | 0 |
| 표기만 다름 | 자모 분리(NFD) | 12 | 12 | 0 | 0 |
| 표기만 다름 | 조사 정리(을(를)→을 등) | 12 | 0 | 12 | 0 |
| 쪽 오류 | 그대로 복사, 쪽 번호가 2쪽 이상 어긋남 | 20 | 0 | 20 | 0 |
| 스캔본 | 글자층 없는 문서 | 10 | 0 | 0 | 10 |

**결과**

- 지어낸 인용문 60건 중 60건을 환각 의심으로 표시.
- 뜻을 바꾼 인용문(숫자·주기·이하/미만) 60건 중 60건을 환각 의심으로 표시.
- 정상 인용문 80건 중 잘못 의심한 것 0건.
- 표기만 다른 인용문 60건 중 36건을 의심으로 표시(뜻은 같음). 글자가 정확히 일치해야 통과시키는 방식의 대가입니다.
- 스캔본 10건은 모두 확인 불가.

**한계**

- 대조는 "인용문 글자가 원문에 있는가"만 봅니다. 인용문은 진짜인데 요약·주기 필드가 틀린 경우는 잡지 못합니다.
- 합성 문서는 글자층이 깨끗합니다. 실제 PDF의 글자 깨짐(한자, 표 안 줄바꿈, 머리말 끼어듦)은 표본에 없습니다.
- **실제 LLM 추출은 재지 못했습니다.** 측정 환경에 `ANTHROPIC_API_KEY`·`GEMINI_API_KEY`·`OPENAI_API_KEY`가 없어서, "LLM이 뽑은 의무 중 원문 대조를 통과한 비율"은 값이 없습니다. 공개 문서 2건으로 잰 추출 재현율·정밀도는 [EXTRACTION_EVAL_RESULTS.md](../EXTRACTION_EVAL_RESULTS.md)에 있습니다.

## 2. 허가증 버전 비교 (`DiffEngine`)

새 허가증의 조건을 이전 버전과 짝지어 "추가 / 삭제 / 변경 / 경미 / 변경 없음"으로 나누는 로직입니다. LLM·DB 없이 엔진만 쟀고, 짝짓기 기준은 앱 기본값(같은 번호 0.6, 유사도 0.5)입니다.

**방법** (`DiffMeasurement`): 합성 허가증 쌍 3개. 쌍마다 이전 조건 100개에 아래 수정을 하나씩 가하고, 새 조건 10개를 추가했습니다(조건 합계 330개). 기대 분류는 생성기가 한 수정입니다.

| 생성기가 한 수정 → 기대 분류 | 주기 필드가 본문을 따라 바뀜 | 주기 필드가 이전 값 그대로 |
|---|---|---|
| 그대로 → 변경 없음 | 60/60 | 60/60 |
| 띄어쓰기만 → 변경 없음 | 30/30 | 30/30 |
| 숫자 변경 → 변경 | 30/30 | 30/30 |
| "이하"→"미만" → 변경 | 30/30 | 30/30 |
| 주기 변경(월·분기·반기·연) → 변경 | 30/30 | **0/30** (모두 경미) |
| 어미 변경 → 경미 | 30/30 | 30/30 |
| 전각 숫자·조사 정리 → 경미 | 30/30 | 30/30 |
| 번호만 변경 → 변경 없음(원래 조건과 짝) | 30/30 | 30/30 |
| 삭제 → 삭제 | 7/30 | 7/30 |
| 추가 → 추가 | 7/30 | 7/30 |
| **전체** | **284/330 (86.1%)** | **254/330 (77.0%)** |

"주기 필드"는 추출 결과의 `frequency` 값입니다. 왼쪽 열은 새 허가증에서 주기 필드도 본문대로 추출된 경우, 오른쪽 열은 본문의 주기 단어만 바뀌고 필드는 이전과 같은 경우입니다(추출이 놓쳤거나, "주 1회"·"일 1회"처럼 둘 다 `OTHER`로 들어가는 주기).

**결과**

- 숫자·주기·이하/미만이 바뀐 조건 90건 중 "변경"으로 분류하지 못한 것: 주기 필드가 따라 바뀌면 0건, 그대로면 30건(주기 변경 30건 전부).
- 표현만 바뀐 조건 60건은 60건 모두 "경미".
- 삭제한 조건 30건 중 23건은 "삭제"가 아니라 새로 추가된 조건과 짝지어져 "변경"(22건)·"경미"(1건)로 나왔습니다. 23건 모두 "짝 확인 필요" 표시가 붙었습니다.
- 비교 1회(100 × 100 조건)는 10ms 안팎입니다.

**번호가 밀린 경우** (같은 테스트의 `every_number_shifted_by_one`): 맨 앞에 조건 1개가 추가되어 번호가 전부 1씩 밀리고 본문은 그대로인 쌍 3개(조건 300개).

- 원래 조건과 다시 짝지어 "변경 없음"으로 본 조건: 300건 중 198건(66.0%).
- 나머지 102건 중 41건은 "짝 확인 필요" 표시가 있고, **61건은 표시 없이** 다른 조건과 짝지어졌습니다(변경 56, 경미 4, 삭제 1).

**한계**

- 문장 틀이 3종뿐이라 조건끼리 실제 허가증보다 많이 닮았습니다. 삭제·추가·번호 밀림 결과는 짝짓기에 불리한 조건에서 나온 값이고, 실제 문서에서 얼마나 나오는지는 재지 않았습니다.
- 숫자·주기 판정 자체(같은 번호로 바르게 짝지어진 뒤의 판정)는 틀 수와 무관합니다.

## 3. 조치 업무 중복 방지 (`EmissionController` + `ExceedanceAlerts`)

한도를 넘은 측정값이 저장되면 조치 업무를 만들되, 같은 배출구·항목에 열린 업무가 있으면 기록만 덧붙이는 기능입니다. 저장할 때 배출구 행을 `SELECT ... FOR UPDATE`로 잠급니다.

**방법** (`CorrectiveConcurrencyMeasurement`): 배출구 1곳(CO 한도 30ppm)에 초과 측정값(45ppm) 50건을 스레드 50개로 동시에 저장. 5회 반복.

- 잠금 있음: 실제 API(`POST /api/emission-points/{id}/measurements`)를 MockMvc로 호출.
- 잠금 없음(대조군): 테스트 안에서 같은 측정값 INSERT와 같은 `ExceedanceAlerts.raise`를 한 트랜잭션으로 실행하되, 배출구 행 잠금만 뺐습니다. 운영 코드는 바꾸지 않았습니다.

| 구성 | 회차별 열린 조치 업무 수 | 저장된 측정값 | 50건 처리 시간 |
|---|---|---|---|
| 잠금 있음 | 1, 1, 1, 1, 1 | 50건씩 | 중앙값 238ms (202~384) |
| 잠금 없음(대조군) | 10, 10, 10, 10, 9 | 50건씩 | 중앙값 35ms (32~64) |

**결과**: 잠금이 있으면 5회 모두 조치 업무 1건이 열리고 나머지 49건은 그 업무의 기록으로 붙었습니다. 잠금이 없으면 평균 9.8건이 열렸습니다.

**한계**

- 대조군의 9~10건은 커넥션 풀 크기(10)와 같습니다. 동시에 열리는 트랜잭션 수만큼 중복이 생긴다는 뜻이고, 풀이 크면 더 늘 수 있습니다.
- 두 구성의 시간은 비교하면 안 됩니다. 잠금 있음은 HTTP·인증·JSON 계층을 거치고, 대조군은 거치지 않습니다.
- MockMvc 호출이라 실제 네트워크 요청은 아닙니다. 서버 1대 기준입니다.

## 4. 기한 알림 배치 (`NotificationJob`)

매일 기한 이벤트를 읽어 D-90/60/30/7 단계 알림을 만들고 사용자별 요약 메일을 보내는 배치입니다.

**방법** (`NotificationBatchMeasurement`): 프로젝트 100개(구성원 3명씩, 사용자 20명). 기한 이벤트 i의 기한은 오늘 + (i mod 120)일, 짝수 i는 담당자 1명에게, 홀수 i는 구성원 3명 모두에게 알립니다. 기대 알림 수는 이 규칙을 따로 계산한 값입니다.

**4-a. 배치 1회 실행**

| 기한 이벤트 | 기대 알림 | 생성된 알림 | 1회 실행 시간 | 같은 날 재실행 시 새 알림 | 재실행 시간 | 요약 메일 | 메일 재실행 |
|---|---|---|---|---|---|---|---|
| 1,000건 | 1,528건 | 1,528건 | 중앙값 1.0초 (0.8~1.8, 5회) | 0건 | 0.3초 | 20통(사용자 20명) | 0통 |
| 10,000건 | 15,103건 | 15,103건 | 중앙값 13.1초 (10.0~16.6, 3회) | 0건 | 9.4초 | 20통(사용자 20명) | 0통 |

단계별 건수(D-7 / 30 / 60 / 90)도 기대값과 같았습니다: 1,000건에서 143 / 405 / 500 / 480, 10,000건에서 1,343 / 3,780 / 5,000 / 4,980.

**4-b. 125일간 매일 실행**: 기한 이벤트 1,000건(기한은 시작일 + 100~119일, 알림 대상 2,000쌍)에 대해 시계를 하루씩 옮기며 배치를 125회 실행.

- 기대 알림 8,000건(2,000쌍 × 4단계) 중 8,000건 생성.
- D-90/60/30/7을 정확히 한 번씩 받은 (이벤트, 사용자) 쌍: 2,000쌍 중 2,000쌍. 중복 0건.
- 125회 실행 합계 40.6초.

**한계**

- 메일은 메모리에 쌓는 가짜 구현이라 SMTP 시간은 빠져 있습니다.
- 배치가 실행 도중 죽었다가 다시 도는 경우는 재지 않았습니다(같은 날 재실행만 확인).

## 5. 법령 개정 배치·영향 판정 (`AmendmentBatch` + `LawImpacts`)

법제처 개정 목록에서 감시 중인 법령의 새 버전을 찾아 저장하고, 연결된 인허가 항목마다 "직접 영향 / 참고 / 알림 없음"을 판정하는 배치입니다.

**방법** (`LawBatchMeasurement`): 법제처 응답은 저장소에 녹화해 둔 2026-10-01 픽스처(폐기물관리법 시행규칙 일부개정, 제10조만 변경)입니다. 프로젝트 50개, 인허가 항목 N건을 아래 8가지 방식으로 고르게 연결했습니다. 정답은 설계 규칙을 연결 방식별로 적은 것이고, 판정 코드(`ImpactRule`)를 불러 만들지 않았습니다.

| 연결 방식 | 정답 | 1,000건 | 10,000건 |
|---|---|---|---|
| 개정 법령, 조문 미지정 | 직접 | 125/125 | 1,250/1,250 |
| 개정 법령, 바뀐 조문(제10조) | 직접 | 125/125 | 1,250/1,250 |
| 개정 법령, 다른 조문(제11조) | 참고 | 125/125 | 1,250/1,250 |
| 상위 법률(폐기물관리법)에 연결 | 직접 | 125/125 | 1,250/1,250 |
| 관계없는 법령(건축법) | 알림 없음 | 125/125 | 1,250/1,250 |
| 개정 법령이지만 완료된 인허가 | 알림 없음 | 125/125 | 1,250/1,250 |
| 공포일 뒤에 만든 연결 | 알림 없음 | 125/125 | 1,250/1,250 |
| 다른 조문 + 상위 법률 둘 다 | 직접 | 125/125 | 1,250/1,250 |

| 인허가 항목 | 정답과 일치 | 생성된 영향(직접 / 참고) | 1회 실행 시간 | 재실행 시 새 영향 | 메일 | 재실행 시 메일 |
|---|---|---|---|---|---|---|
| 1,000건 | 1,000/1,000 | 625건 (500 / 125) | 중앙값 1.3초 (0.7~1.9, 5회) | 0건 | 10통(책임자 10명) | 0통 |
| 10,000건 | 10,000/10,000 | 6,250건 (5,000 / 1,250) | 중앙값 10.3초 (6.5~24.5, 3회) | 0건 | 10통(책임자 10명) | 0통 |

재실행은 커서를 전날로 되돌려 같은 날짜를 다시 처리한 것입니다.

**한계**

- 개정은 픽스처 1건(일부개정, 조문 1개)입니다. 폐지·타법개정·전부개정과 별표 변경은 이 측정에 없고 단위 테스트(`ImpactRuleTest`)에만 있습니다.
- 법제처 API 호출 시간과 실패는 포함되지 않습니다(픽스처는 즉시 응답).
- 정답이 설계 규칙에서 나오므로, 규칙 자체가 실무에 맞는지는 이 측정으로 알 수 없습니다.

## 6. 이행 보고서 XLSX (`ComplianceReport`)

**6-a. 5,000행 상한 근처의 시간과 메모리** (`XlsxExportMeasurement`): 배출구 1곳에 측정값 N행을 넣고 조회(`load`) + 파일 생성(`xlsx`)을 준비 1회 뒤 5회 실행. 만든 파일은 다시 열어 행 수를 셌습니다.

| 측정 결과 행 수 | 결과 | 조회+생성 시간 | 그중 파일 생성 | 생성 중 할당한 메모리 | 파일 크기 | 다시 열어 센 행 수 |
|---|---|---|---|---|---|---|
| 1,000행 | 생성 | 중앙값 37ms (30~49) | 24ms | 12.5MB | 43KB | 1,000행 |
| 4,999행 | 생성 | 중앙값 66ms (64~75) | 53ms | 46.4MB | 188KB | 4,999행 |
| 5,000행 | 생성 | 중앙값 77ms (74~81) | 54ms | 46.2MB | 188KB | 5,000행 |
| 5,001행 | 거절(422) | 26ms | - | - | - | - |

"할당한 메모리"는 그 스레드가 조회부터 파일 완성까지 할당한 총량입니다(`ThreadMXBean`). 측정 중 GC가 돌지 않아 힙 최대 사용량도 같은 값(5,000행에서 46MB)으로 나왔습니다. 동시에 살아 있어야 하는 메모리는 이보다 작지만 따로 재지 못했습니다.

**6-b. 수식으로 시작하는 값**: 배출구 이름 100건을 보고서로 내보낸 뒤 파일을 다시 열어 셀 종류를 확인했습니다. "위험"의 기준은 OWASP CSV Injection 목록(첫 글자가 `=`, `+`, `-`, `@`, 탭, CR)입니다.

| 표본 | 건수 | 문자 셀(수식 셀 아님) | 앞에 `'`를 붙여 저장 | 원래 값 그대로 |
|---|---|---|---|---|
| 위험: 첫 글자가 `=` `+` `-` `@` 탭 CR (6종 × 내용 10종) | 60 | 60/60 | 60/60 | 0 |
| 일반 이름(기호가 중간에 있음) | 20 | 20/20 | 0 | 20/20 |
| 변형: 공백·전각 `＝`·줄바꿈·따옴표 뒤에 `=` | 20 | 20/20 | 0/20 | 20 |

**결과**: 수식으로 시작하는 값 60건 중 60건이 문자 셀로 저장됐고, 일반 이름 20건은 20건 모두 바뀌지 않았습니다.

**한계**

- 셀 종류는 POI로 다시 열어 확인했습니다. Excel에서 직접 열어 보지는 않았습니다(앞에 붙인 `'`가 화면에 보이는지 포함).
- 변형 20건은 `'`가 붙지 않습니다. XLSX에서는 문자 셀이라 실행되지 않지만, 사용자가 이 파일을 CSV로 다시 저장하면 보호되지 않습니다.
- 측정 결과 시트만 5,000행으로 채웠습니다. 다른 시트(의무사항·조치)는 비어 있습니다.

## 드러난 문제 (고치지 않음)

1. **주기 단어만 바뀌면 "경미"로 분류됩니다** (버전 비교). 본문이 "분기 1회"에서 "반기 1회"로 바뀌어도 `frequency` 필드가 같으면 숫자 토큰이 같아 "경미"가 됩니다(30건 중 30건). 추출이 주기 필드를 놓친 경우와, "주 1회"→"일 1회"처럼 둘 다 `OTHER`인 경우에 해당합니다. 기존 `DiffEngineTest`의 "분기 1회 → 월 1회 = MINOR"와 같은 현상입니다.
2. **번호가 밀리면 표시 없이 엉뚱한 조건과 짝지어집니다** (버전 비교). 같은 번호끼리 유사도가 0.6을 넘으면 "짝 확인 필요" 표시 없이 짝이 확정됩니다. 문장이 서로 닮은 조건에서 300건 중 61건이 그렇게 됐습니다.
3. **삭제된 조건과 새 조건이 서로 짝지어집니다** (버전 비교). 30건 중 23건. "짝 확인 필요" 표시는 붙습니다.
4. **표기만 다른 인용문이 환각 의심으로 표시됩니다** (원문 대조). 어미·전각 숫자·조사 차이 36건. 쪽 번호가 2쪽 이상 틀린 정상 인용문 20건도 의심으로 표시됩니다. 의심 쪽으로 틀리는 것이라 안전한 방향이지만 검토자가 볼 건수가 늘어납니다.
5. **기한 알림 배치는 재실행도 느립니다.** 10,000건에서 새 알림이 0건인 재실행에 9.4초가 걸렸습니다. 알림 대상마다 존재 여부 조회와 저장을 한 건씩 하기 때문으로 보입니다. 하루 한 번 도는 배치라 지금 규모에서는 문제가 아닙니다.
6. **XLSX는 쓰기만 스트리밍입니다.** 조회 결과 전체를 리스트로 메모리에 올리고 완성된 파일도 바이트 배열로 돌려줍니다. 5,000행 상한 덕분에 46MB 할당에 그칩니다.
