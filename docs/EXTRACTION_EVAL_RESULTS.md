## 읽는 법과 한계

- **조건번호 일치율은 이 문서들에서 품질 지표가 되지 못합니다.** 두 문서 모두 조건마다 번호가 없고 목차("2. 가.") 아래 ○ 항목이 나열됩니다. 모델마다 목차를 적는 방식이 달라("Ⅱ-2-가 동·식물상", "가. 동·식물상") 정확 일치는 0%이고, 같은 모델도 문서마다 표기가 달라집니다. 조건마다 번호가 있는 허가증으로 따로 재야 합니다.
- **정밀도 100%는 "문서에 없는 의무를 지어내지 않았다"는 뜻입니다.** 정답표가 채점 대상(협의내용, 사업자 행정사항) 밖의 본문도 `참고` 행으로 담고 있어, 본문에 있는 내용을 뽑으면 오답이 되지 않습니다.
- 주기는 주기가 적힌 채점 조건이 문서당 1~3개(합계 4개)뿐이라 표본이 작고, 정답표 판정 하나에 크게 흔들립니다. 검토 전후로 Claude가 3/6 → 5/5로 바뀐 것은 모델이 아니라 "사후환경영향조사서 제출"(12개월 조사 후 2개월 이내 제출)을 주기로 보느냐는 정답표 판정 때문입니다. 제공자 간 우열의 근거로 쓰지 마십시오.
- OpenAI는 항목을 가장 잘게 나눠 가장 많이 뽑았고(검토할 항목이 많음), Gemini는 문서당 11~33개만 뽑았습니다. Claude가 놓친 것은 주로 "1. 총괄"의 일반 조항입니다.
- 비용은 실행 때 기록된 토큰 수 × 단가(100만 토큰당 입력/출력 USD: Claude 2/10, Gemini 0.75/3.75, OpenAI 1/5)로 계산한 값입니다. Gemini·OpenAI 단가는 공식 가격표로 확인하지 않았습니다.
- 회사 문서는 쓰지 않았습니다.

## 정답표 검토 (2026-11-15)

정답표 초안을 만든 쪽(Claude)이 자기 분할 방식에 맞춰 채점하는 편향을 줄이려고, 고치기 전에 규칙을 글로 정하고 기계적으로 적용했습니다.

- 단위: 원문 "○" 1개 = 정답 1행. 그 아래 ╺·-·*·※·표는 같은 행에 합침. 한 ○ 안의 의무가 여러 개여도 나누지 않음.
- 채점 범위: Ⅱ. 협의내용과 Ⅴ. 2. 사업자의 모든 ○(의무 문형이면 해석 규칙·권리에 가까운 것도 채점, 경계 행으로 표시). Ⅲ·Ⅳ·Ⅴ.1은 참고.
- 조건번호: 목차 경로. 주기: 그 ○ 본문에 반복 간격이 적힌 경우만. 기한("20일 이내", "12개월 조사 후 2개월 이내 제출")과 간격 없는 "주기적으로"는 비움.

PDF 글자층에서 ○ 항목을 기계적으로 나눠 정답표와 대조한 결과, 두 문서 모두 항목 수(44, 62)·순서·목차·내용(글자·숫자 기준)이 모두 일치했습니다. 빠진 조건, 조건이 아닌 행, 잘못 나뉜 행은 없었고, **주기 3칸만 바뀌었습니다**(사후환경영향조사서 제출 2행 ANNUAL → 빈칸, "일일 처리량을 일지로 관리" 1행 빈칸 → OTHER).

저장된 응답 원문을 다시 채점(`extractionEval --args="rescore <폴더>"`, API 호출 없음)한 결과 **재현율·정밀도는 9개 실행 모두 그대로**이고 주기 일치만 바뀌었습니다. 초안 정답표로 같은 재채점을 돌려 원래 값이 그대로 나오는 것을 먼저 확인했습니다.

전문가가 봐야 할 경계 행: Ⅱ.1 "협의내용 우선 적용"(해석 규칙), Ⅴ.2 "90일 이내 이의신청"(권리), Ⅴ.2 사후환경영향조사서 제출의 주기, Ⅱ.2.다 "일일 처리량 일지"와 "우기 전·후 준설"의 주기, Ⅱ.1 총괄 일반 조항을 개별 조건으로 셀지(Claude가 놓친 행이 주로 여기).

### 실무자 판정 (2026-11-17)

경계 행 9개를 설계사 실무자(이 프로젝트 작성자)에게 실무 질문으로 물어 정했습니다.

- 총괄 이행 조항("협의내용을 철저히 이행", "협의내용 우선 적용") 3행: 할 일이 아님 → 채점 제외.
- "90일 이내 이의신청" 2행: 사업자의 권리라 할 일이 아님 → 채점 제외.
- 사후환경영향조사서 제출 2행: 주기 ANNUAL. 근거는 환경영향평가법 시행규칙 제19조제4항입니다. 조사기간이 끝난 날부터 60일 이내에 통보하되, 조사기간이 1년 이상이면 연도별 결과를 매년 통보합니다(국가법령정보센터, 2026-11-17 확인).
- "우기 전·후 준설", "일일 처리량 일지"는 그대로 둡니다(주기 없음 / OTHER).

채점 대상이 106 → 101행이 됐고, 저장된 응답을 다시 채점했습니다(API 호출 없음). Claude가 놓친 행이 주로 총괄 조항이었기 때문에 Claude 재현율이 가장 많이 올랐습니다. 정답표 작성·2차 검토는 여전히 Claude가 했고, 사람은 이 9행만 판정했습니다.

# 문서 → 일정 추출: 보류(held-out) 세트 측정 (2026-11-17)

개발 세트(가온시 12건)는 문서·정규식·프롬프트를 같은 세트로 함께 만들고 보정해서 성과로 쓸 수 없습니다.
그래서 새 세트를 따로 만들어, 정답을 고정한 뒤 추출기를 손대지 않고 돌렸습니다.

## 방법

- 세트: 솔빛군(가상) 문서 13건 — 입찰공고 3, 현장설명서 2, 과업내용서·과업지시서 2, 예정공정표 1, 심의 일정 안내 등 공문 3, 회의록 2.
- 형식을 섞었습니다: 절대 날짜, 기준일 규칙(현장설명일·적격자 통보일·착공일·착수일·계약일·준공일·심의일), 표, 정기 보고(매월·분기·격주·매주), 연도 없는 날짜.
- 정답: 날짜 단위 64개, 함정 24개(공고일·시행일·작성일·회의 당일·법령 제정일·과거 실적).
- 정답 고정: 커밋 `2f26a60`(문서·정답표·채점 방식을 한 커밋에). 이 커밋 뒤에 추출기를 처음 돌렸습니다.
- 추출기: 로컬 규칙 기반(`ScheduleEval.rules`)과 앱의 LLM 경로(`SchedulePrompt` + `Extraction.scheduleRows`, `claude-sonnet-5-5`, dev 기본 제공자). 둘 다 수정하지 않았습니다.
- 채점: 개발 세트와 같은 날짜 단위 비교. 제목은 보지 않습니다.
  - 같은 문서에 기준일이 적혀 있으면 규칙과 풀린 날짜 둘 다 정답으로 인정합니다(`A|B`). 예: `REVIEW-7D|2028-07-19`.
  - 함정 날짜를 뽑으면 오검출이고, 따로 셉니다.
- 실행: `./gradlew scheduleEval --args="src/test/resources/schedule-eval-heldout rule,claude"`. 원 출력은 `backend/src/test/resources/schedule-eval-heldout/runs/`.

## 보인 실패 (고치지 않음, 다음 작업)

이번에는 프롬프트·규칙을 바꾸지 않았습니다. 고치면 또 새 보류 세트로 다시 재야 합니다.

- **공정표 표의 시작·종료일:** 예정공정표 11개 중 5개만 찾았습니다(1·2차 같음). 공정 행의 종료일·시작일을 대부분 놓쳤습니다. 채점 코드가 공정(TASK) 행의 종료일을 키로 만들지 않는 탓인지, 모델이 행을 안 낸 탓인지는 아직 확인하지 않았습니다.
- **여러 날 일정의 끝날:** 출장·평가 기간의 마지막 날을 자주 놓칩니다(`9. 20.~9. 21.`, `12월 4일 ~ 12월 5일`, `6월 7일 ~ 6월 9일`).
- **정기 보고:** "분기마다", "매주 금요일 주간보고"를 놓친 경우가 있습니다.
- **기준일 규칙:** "적격자 통보일로부터 7일 이내", "착수 후 8개월 시점"을 회차에 따라 놓칩니다.
- **회의록의 회의 당일:** 회의 날짜 자체를 일정으로 올렸습니다(함정 1건).
- **규칙 기반:** 함정 날짜를 거르지 못합니다. "계약 체결일로부터 7일", "적격자 통보 후 7일"처럼 기준일 사이에 다른 말이 끼면 놓치고, 연도 없는 `9. 21.`도 놓칩니다.
